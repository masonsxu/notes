# 《用好 opencode：高阶手法与提问之道》原始材料

> **目标受众**：已掌握 opencode 基础操作（会安装、会用 Plan/Build、配过 AGENTS.md）的工程师
> **核心目的**：掌握"用得准、用得好"的高阶手法——提问技巧、高阶配置、上下文管理；并以一次完整实战（用 opencode 制作 PPT）打通工程化使用心法
> **使用方式**：本文档为 PPT 原始材料；第八章由原《大模型实践落地》内容融入而成

---

## 一、为什么"用得好"比"用得多"重要

### 1.1 核心公式

```
输出质量 = 提问质量 × 配置质量 × 上下文管理
```

- 工具能力是固定的，**使用手法决定结果上限**
- 同样的 opencode，有人"一句话干成一件活"，有人"反复返工改不对"

### 1.2 常见"用不好"现象

| 现象 | 根因 | 本篇对应章节 |
| --- | --- | --- |
| 答非所问、方向跑偏 | 提问太模糊，上下文不足 | 二、Prompt 工程 |
| 反复返工、改了又改 | 需求没说清，确认门缺失 | 二、Prompt 工程 / 八、实战方法论 |
| 越聊越慢、上下文爆炸 | 不会管理会话与上下文 | 六、Context 管理 |
| 输出不专业、术语误解 | AGENTS.md 没配好 | 三、AGENTS.md 高阶配置 |
| 改错文件、误伤代码 | 没有 Plan 先行 | 四、Plan-Build 深度工作流 |

### 1.3 本篇路线图

```
提问手法（二） → 高阶配置（三、四、五） → 上下文管理（六）
     → 数据输入（七） → 工程化实战（八） → 团队落地（九）
```

## 二、Prompt 工程：任务越具体，效果越好

### 2.1 黄金法则

> **给 opencode 的信息越具体，输出的结果越准确。**
> 它不了解你的项目细节，你的每一条背景、每一个约束，都在帮它减少猜测。

### 2.2 模糊 vs 具体对比

#### 模糊指令（效果差）

```
帮我排查这个报错。
```

**问题**：
- 没说是哪个系统、哪个文件、什么现象
- opencode 只能给一套通用排查步骤，不具针对性

#### 具体指令（效果极佳）

```
我在跑一个数据处理脚本 data_analyzer.py，执行到第 42 行报
KeyError: 'wafer_id'。数据文件是 ./data/test_results.csv，
第 1 行是表头。请帮我：
1. 读取脚本和 CSV，定位 KeyError 的根因
2. 检查 CSV 表头与脚本字段引用是否一致
3. 修复脚本，并验证能正常跑通
```

**为什么效果好**：位置、现象、数据文件、期望动作全部交代清楚，opencode 无需猜测。

### 2.3 结构化五段式模板

```
【背景】  项目/场景描述、技术栈、已有条件
【目标】  期望实现的功能、验收标准
【约束】  性能要求、兼容性、安全限制、不能动什么
【输入】  相关文件路径（代码、数据、配置）
【输出】  期望的文件格式、保存位置、是否需要测试
```

> 不是每次都写满五段——**缺哪个写哪个**。核心是把你脑子里"理所当然"的细节显式说出来。

### 2.4 三个优化技巧

1. **给示例**：提供输入/输出样例，比一百句描述更有效
2. **分步骤指令**：把任务拆成有序步骤（先读…再…然后…最后…），opencode 不会跳步
3. **明确输出格式**：指定 Markdown 表格 / 脚本结构 / 文件命名，产出直接可用

## 三、AGENTS.md 高阶配置

### 3.1 双层配置与优先级

```
优先级：项目级 AGENTS.md > 全局 AGENTS.md
位置：
  <项目根目录>/AGENTS.md        # 项目级：随仓库共享，团队统一
  ~/.config/opencode/AGENTS.md  # 全局级：个人规则，跨项目生效
```

- 项目级写**团队要统一的**（领域术语、编码规范、目录约定）
- 全局级写**个人私有的**（个人偏好、常用工具链、通用习惯）

### 3.2 opencode.json：额外规则文件

除了 AGENTS.md，可在 `opencode.json` 里用 `instructions` 字段指定更多规则文件：

```json
{
  "$schema": "https://opencode.ai/config.json",
  "instructions": [
    "docs/development-standards.md",
    "test/testing-guidelines.md"
  ]
}
```

- 适合团队已有规范文档的场景：不重复搬运，直接引用
- 支持 glob 通配（如 `packages/*/AGENTS.md`）

### 3.3 术语消歧义

专业语境下，同一个词模型可能按通用含义理解——用 AGENTS.md 显式定义：

| 术语 | 通用理解 | 专业理解（需配置） |
| --- | --- | --- |
| Yield | 产量、收益 | 良率：合格品占总数的比例 |
| Probe | 探测、探查 | 探针测试：晶圆级电性测试 |
| DOE | 能量守恒公式（Design of Experiment 缩写易混） | 实验设计：用于优化工艺参数 |
| SECS/GEM | 无 | 半导体设备通讯标准协议 |

### 3.4 完整模板与分项目配置

```markdown
# 角色与背景
你是一个 [部门] 的 [角色]，负责 [职责1]、[职责2]。

# 专业术语
- 术语A: 定义（区分于通用含义）
- 术语B: 定义

# 代码与输出风格
- 优先 [语言/框架]，使用 [依赖管理器]
- 代码必须 [健壮性要求]
- 回答风格: 专业、简洁、结果导向；复杂问题分步骤

# 安全与约束
- 涉及 [敏感环境] 先确认安全步骤
- 修改前备份，不直接删除文件
```

> **分项目配置**：不同项目在各自根目录放独立的 AGENTS.md，写该项目独有的信息（数据目录结构、特殊编码要求等），全局文件保持精简。

## 四、Plan-Build 深度工作流

### 4.1 复杂任务的 Plan 拆解

Plan 模式不只是"列个步骤"，好 Plan 包含三件事：

```
1. 任务拆解（TODO 列表，每步有验收点）
2. 涉及文件清单（明确会改哪些文件，避免误伤）
3. 风险评估（数据风险 / 兼容风险 / 回滚方案）
```

### 4.2 三个加速技巧

1. **并行任务拆解**：把互不依赖的模块拆成独立任务，让 opencode 分头规划
2. **增量式开发**：先做最小可用版本（MVP），跑通再逐步加功能
3. **复用已有代码**：明确引用项目里已有的模块，要求"保持风格一致"

### 4.3 多轮规划：先粗后细

- 第一轮：让 opencode 给出整体架构与阶段划分
- 第二轮：针对你关心的阶段深入拆解
- 每轮确认后再进入下一步——**确认门要重，返工才少**

## 五、Skill 深度与组合拳

### 5.1 Skill 的进阶用法

- 单个 Skill 解决单领域问题；**组合多个 Skill** 才能跑通复杂流程
- 用对 Skill = 让 opencode 用"专家方法"而不是"通用方法"干活

### 5.2 提问框架 + Skill 组合

```
【澄清需求】 需求澄清类 Skill：反问关键细节，把模糊需求问清楚
     │
     ▼
【规划方案】 planning Skill：结构化拆解任务
     │
     ▼
【执行落地】 Build 模式 + 领域 Skill（写代码/做PPT/查资料）
     │
     ▼
【审查把关】 review 类 Skill：自查质量、抓隐患
```

### 5.3 常见高阶 Skill 场景

| 场景 | 组合方式 |
| --- | --- |
| 疑难 Bug 定位 | 需求澄清 → 调试 Skill → 修复 → review |
| 新功能开发 | planning → Build → 测试 → review |
| 技术调研 | web search 检索 → 整理成对比报告 |
| 文档/PPT 制作 | 内容梳理 Skill → 设计 Skill → 渲染 QA |

## 六、Context 管理：防止上下文爆炸

### 6.1 上下文如何累积

```
对话每多一轮，历史上下文就长一截
    ├── 输入侧：系统提示 + AGENTS.md + 历史对话 + 你的输入
    └── 输出侧：opencode 的回复内容
```

- 对话越长 → 输入 Token 越多 → 响应变慢、花费增加、**注意力被稀释**
- 不是"聊得越多越好"，而是"该记的记、该扔的扔"

### 6.2 /compact 的时机

`/compact`（别名 `/summarize`）会把当前会话压缩成一份摘要，保留要点、丢弃细节。

**适合用的时机**：
- 响应明显变慢，或接近上下文上限
- 长任务已完成核心部分，只剩收尾
- 话题从 A 转向 B，但还想保留 A 的结论

### 6.3 会话策略

| 情况 | 策略 |
| --- | --- |
| 新任务 | `/new` 开新会话，别和历史混在一起 |
| 长任务中途 | 阶段性 `/compact`，保持上下文精简 |
| 中断后继续 | `/sessions` 续接，或 `opencode attach --continue` |
| 方向跑偏 | 果断 `/new` 重来，不要在错误方向上耗 Token |

### 6.4 输入减肥

- **不粘贴大文件**：让 opencode 自己读文件（它读文件比粘贴高效得多）
- **预处理**：超大日志先用命令提取关键行，再让它分析
- **结构化输入**：把数据整理成表格/JSON 再喂，比原始文本省 Token 且更准

```
# 反例：把 100MB 日志整个贴进对话
# 正例：先提取关键信息，再交给 opencode
grep -E "ERROR|WARN" large_log.txt > filtered_errors.txt
# 然后：请分析 filtered_errors.txt 的错误分布
```

## 七、数据输入与实验设计（DOE）

### 7.1 三种数据输入方式

| 方式 | 适用场景 | 示例 |
| --- | --- | --- |
| ① 读取项目文件 | 数据就在工作区 | "请读取 ./data/rc_data.csv 并分析" |
| ② 粘贴关键数据 | 少量结构化数据 | 贴一段汇总统计表让它分析趋势 |
| ③ 提供文件路径 | 数据在别处 | "原始数据在 /data/raw.csv，处理后数据在 /data/processed.csv" |

> 原则：**能让它自己读的就不粘贴**；必须粘贴时给结构化数据。

### 7.2 基于已有数据设计 DOE

```
[ 已有数据 ] → [ 数据分析 ] → [ 识别问题 ] → [ 设计 DOE ]
                                              ├── 确定因子
                                              ├── 确定水平
                                              ├── 选择设计类型
                                              └── 生成实验矩阵
```

**指令示例**：
```
这是最近 3 批次的接触电阻数据 rc_data.json：平均 45mΩ、
标准差 3.5mΩ、异常 Die 集中在边缘。请设计一个 3 因子
2 水平的 DOE：针尖压力 50-80μm、清洗周期 50-100 次、
测试时间 10-30ms，目标是降低标准差、提升 CPK 到 1.5 以上。
请给出实验矩阵与每组实验的采样建议。
```

## 八、【实战】用 opencode 把文字材料变成咨询级 PPT

> 本章由原《大模型实践落地》PPT3 内容融入。这不是一次普通演示——它是一次真实项目，**每一步都在示范"怎么把 opencode 用到位"**。注意看的不只是"做了什么"，更是"用什么手法做的"。

### 8.1 案例背景与目标

- 任务：把两份 Markdown 文字材料，做成两份可直接演示、**100% 可编辑**的咨询级 PPT
- 关键约束：不用模板化的 AI 生成风格；不臆造数据；可复现
- 结果：两份 PPT 共 35 页全部原生文本/形状/表格，0 张图片，可编辑

### 8.2 七步工作流总览

```
1. 需求澄清 + 证据表   → 建 MBB 证据表，每个事实标来源
2. 视觉风格选择        → 8 张样张让用户直接看图选
3. 环境能力核查        → 确认渲染链路，缺失如实降级
4. 共享模块搭建        → 视觉系统固化为可复用模块
5. 风格验证样张        → 先做 3 页样张确认，再量产
6. 逐份生产 + 渲染 QA  → 生产、渲染、脚本化自检
7. 方向纠偏            → 发现方向错，先确认新结构再重写
```

### 8.3 每步的手法提炼（这就是 opencode 高阶用法）

| 步骤 | 手法 | 背后的原则 |
| --- | --- | --- |
| ① 证据表先行 | 每个事实/数字标来源、置信度、caveat | **不臆造**：不用常识补材料没有的数据 |
| ② 确认门要重 | 故事线/页数/逐页论点一次确认，再动手 | **先对齐再执行**：避免方向性返工 |
| ③ 环境核查 | 先确认工具链能力（渲染、图像生成），缺失如实告知 | **事实优先**：不假装满足硬门槛 |
| ④ 模块化 | 视觉系统固化成共享模块，两份 PPT 复用 | **复用**：改一处，多处生效 |
| ⑤ 先验证再量产 | 先做 3 页样张给人看，确认后批量生产 | **小步验证**：避免 35 页全返工 |
| ⑥ 脚本化自检 | 用脚本查零尺寸/越界，不靠肉眼 | **可证伪**：用断言代替感觉 |
| ⑦ 果断重写 | 方向错了立即推翻重来，先确认新结构 | **止损**：不在错误方向修补 |

### 8.4 三个"反常识"认知

1. **opencode 的价值在"端到端动手"，不在"聊天"**
   它能生成文件、渲染、自检、迭代，把活真正干完——你负责审核与决策。
2. **环境能力决定方法路径**
   有没有渲染器、有没有图像生成，直接决定能用哪套流程。先核查再动手。
3. **降级不等于失败**
   缺图像生成就如实降级：用原生对象生产 + 渲染 QA，照样交付高质量可编辑 PPT。关键是如实留痕。

### 8.5 踩坑避坑表

| 坑 | 现象 | 解法 |
| --- | --- | --- |
| 意图理解错 | 按材料标题做"成本优化"，用户要的是"用好" | 先确认新结构再重写；材料标题≠真实意图 |
| 图层遮挡 | 连线盖住中心节点 | 先画底层再画上层，注意 z-order |
| 只看得到首页 | 渲染器只导出首页 PNG | 先转 PDF 再按页切图 |
| 缺环境能力 | 无法走标准流程 | 如实降级 + 留痕，不假装满足 |
| 效果数据失真 | 把预估百分比当实测成果 | 统一标"预估/待实测"，或用可观察信号 |

### 8.6 复现 Checklist（把这套手法带走）

- [ ] 通读源材料，建证据表（每条标来源/置信度）
- [ ] 脑暴 2-3 条故事线，推荐 1 条，写 SCR 论证结构
- [ ] 逐页大纲含信息密度与组件清单，和需求方确认
- [ ] 展示视觉样张让用户选定，锁定色板/字号体系
- [ ] 搭共享视觉模块，先做 3 页样张验证
- [ ] 批量生产 + 渲染 + 脚本化自检
- [ ] 渲染图交人审，逐页确认
- [ ] 方向不对 → 先确认新方向与新结构，果断重写

## 九、团队落地与复盘

### 9.1 团队共识

- 统一一份**部门级 AGENTS.md**（术语/规范/风格），新人入职即生效
- 建 **Prompt 模板库**：把高频任务的结构化提问沉淀成模板
- 维护 **Skill 清单**：团队认可的 skill 与使用场景，减少试错

### 9.2 知识沉淀

- 有价值的会话保留/复用，避免重复劳动
- 把"怎么让 opencode 干成某类活"写成 SOP（如本 PPT 的第七章）
- 定期分享实战案例：成功的手法与踩过的坑

### 9.3 效果评估：用可观察信号，不用未实测百分比

| 信号 | 观察方式 |
| --- | --- |
| 采用率 | 团队成员实际使用 opencode 完成任务的频次 |
| 复用数 | 沉淀的模板/Skill/会话被复用的次数 |
| 沉淀量 | AGENTS.md、Prompt 模板、SOP 文档的增量 |

> 原则：**没有实测的数据就标"预估/待实测"**，或改用可观察信号——这是上一章实战方法论的核心纪律。

## 十、FAQ 与收束

### Q1：opencode 回答不准确怎么办？

1. 检查提问是否够具体（回到第二章五段式模板）
2. 检查 AGENTS.md 是否覆盖了领域术语与背景
3. 补充关键上下文：文件路径、错误信息、期望输出

### Q2：对话越聊越慢/越聊越贵怎么办？

1. 用 `/compact` 压缩上下文
2. 无关内容果断 `/new` 开新会话
3. 大文件让 opencode 自己读，别粘贴

### Q3：opencode 改错文件了怎么办？

1. 用 Git 回滚（改之前先提交/确认工作区干净）
2. 关键修改前先 Plan，明确"会动哪些文件"
3. 权限配置收紧：`permission` 里把高风险工具设为 ask

### Q4：不知道用什么模式/手法怎么办？

1. 复杂任务一律先 Plan
2. 需求说不清时先做需求澄清（问清楚再干）
3. 参考第八章的七步工作流：证据表 → 确认门 → 小步验证 → 脚本自检

### 收束

> 工具已经就位，差距在手法。把本章的模板、清单、工作流带走，**用 opencode 把一个真实任务完整走一遍**——这就是最好的学习。
