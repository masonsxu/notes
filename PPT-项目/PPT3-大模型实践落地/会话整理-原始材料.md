# 《大模型实践落地：从文字材料到咨询级 PPT 的全流程复现》

> **文档性质**：本文件是 PPT3 的原始材料，由本次会话的完整过程整理而成。
> **PPT3 定位**：面向新人的"大模型实践落地"教学——照着一步步做，能用大模型把文字材料变成和 PPT1/PPT2 一模一样的可编辑咨询级 PPT。
> **整理原则**：如实记录真实过程（含走错的弯路与纠正），不美化、不遗漏，让新人能复现、能避坑。

---

## 一、项目背景与目标

### 1.1 起点任务
用户提供两份 Markdown 文字材料，要求制作两份 PPT：
- **PPT1**：《公司大模型工具使用入门》——面向部门新人/工程师的入门教学
- **PPT2**：原为《大模型成本优化与高级功能配置》，**中途方向纠偏**后改为《用好大模型：CIMICode 进阶应用与团队落地》——面向 TL/资深工程师

### 1.2 使用的"大模型"是什么
本项目用的"大模型"不是单一聊天模型，而是一个**编程智能体（agent）**——它能读文件、执行命令、写代码、生成 PPTX、调用渲染工具。本会话用的智能体是 **pi**，配合 **cyber-ppt 技能（Skill）**（一套 PPT 制作的方法论与约束）。

> **关键认知**：把大模型当成"能动手的助理"，而不是"只会聊天的机器人"。它的价值在于端到端把活干完（生成文件 + 渲染 + 自检 + 迭代）。

### 1.3 最终交付物
| 交付物 | 页数 | 文件 |
|---|---|---|
| PPT1 入门 | 17 | `PPT1-入门/deck/PPT1-公司大模型工具使用入门.pptx` |
| PPT2 进阶 | 18 | `PPT2-成本优化/deck/PPT2-大模型进阶应用与团队落地.pptx` |
| 视觉风格 | — | 风格4「象牙白 + 深蓝强调」 |
| 可编辑性 | — | 100% 原生文本/形状/表格，0 张图片 |

## 二、技术栈与环境准备

> **实战教训**：动手前先核查环境能力——本项目因为环境缺图像生成、缺渲染器，一度卡住。新人复现时第一步就是把环境装好。

### 2.1 必备工具清单

| 工具 | 用途 | 安装/检查命令 |
|---|---|---|
| **bun** | 运行 PptxGenJS 生成 PPTX | `brew install bun`（或官方脚本） |
| **pptxgenjs** | PPTX 生成引擎（强制使用，禁 python-pptx） | `bun add -g pptxgenjs` |
| **LibreOffice (soffice)** | PPTX → PDF 渲染（视觉 QA 必需） | 官网装到 `/Applications` 或自定义路径 |
| **uv** | Python 环境管理 | `curl -LsSf https://astral.sh/uv/install.sh \| sh` |
| **python-pptx** | PPTX 结构自检（读取对象/越界检查） | `uv pip install python-pptx` |
| **Pillow** | 图像辅助 | `uv pip install Pillow` |
| **PyMuPDF (fitz)** | PDF → 每页 PNG（关键，否则无法逐页看渲染图） | `uv pip install pymupdf` |
| **cyber-ppt 技能** | PPT 方法论与脚本 | 智能体内置 `~/.pi/agent/skills/cyber-ppt/` |

### 2.2 渲染链路（必须打通）
完整链路缺一不可：
```
bun + pptxgenjs  →  PPTX
LibreOffice      →  PDF
PyMuPDF          →  每页 PNG（用于人眼审阅 / 视觉 QA）
```

**踩坑**：LibreOffice 只能直接导出首页 PNG；多页要"先转 PDF，再用 PyMuPDF 切每页"。没装 PyMuPDF 就看不到逐页渲染图。

### 2.3 环境核查命令（复现第一步）
动手前逐项确认：
```bash
bun --version && bun pm ls -g | grep pptxgenjs          # pptxgenjs 在
SOFFICE=".../LibreOffice.app/Contents/MacOS/soffice"
"$SOFFICE" --version                                      # LibreOffice 在
uv run python -c "import pptx,PIL,fitz;print('OK')"      # Python 三件套在
```

## 三、完整工作流（7 步，按真实顺序）

### 步骤 1：需求澄清 + 源材料分析（不要急着画 PPT）

**做了什么**：
1. 通读两份源材料，建立 **MBB 标准证据表**（每个事实/数字/论点都记录来源位置、置信度、caveat）。
   - PPT1 抽取 38 条证据（E01–E38）；PPT2 抽取 36 条（E01–E36）。
2. **内容脑暴**：每份各提 3 条可选故事线，比较论证锋利度、证据强度、受众适配，推荐 1 条。
3. 收敛成 **SCR**（Situation-Complication-Resolution）论证结构。
4. 生成**逐页大纲**：每页含结论标题、角色、证据 ID、图表计划、**信息密度与组件清单**。
5. **第一次确认门**：把证据表 + 故事线 + SCR + 逐页大纲交给用户确认，**用户拍板后才进下一步**。

**关键纪律**：
- 不得用常识补源材料没有的数据。
- 数据冲突如实标注（如"80% 是建议比例，非实测"）。
- 大纲不能只有"页面标题 + 简短描述"，必须有信息密度和组件清单。

**用户当时的 6 项决策**（记录在案）：
1. 页数：PPT1=16（后因 Demo 全加变 17）、PPT2=18
2. 效果数据未实测，只说大概效果
3. 两份 PPT 共用一套视觉风格
4. PPT1 面向新人，手把手教学
5. Demo 全部加上
6. 跨 PPT 互相承接

> **实战教训**：第一次确认要"重"——故事线、页数、逐页论点、密度、组件清单一次性确认，避免后面返工。

### 步骤 2：视觉风格选择（8 张样张门）

**做了什么**：
1. 读取 cyber-ppt 技能的 8 个固定视觉风格。
2. **直接在对话里发送 8 张独立 16:9 样张图片**（不是文字描述、不是拼图）。
3. 每张列出编号、名称、色板、语气、优势、风险。
4. 给出推荐（风格4 深蓝，因为专为科技/AI 设计），**让用户选**。
5. 用户确认能看到 8 张图 + 选定风格4 → 进入逐页蓝图。

**选定**：风格4「象牙白 + 深蓝强调」
- 底色 `#F7F6F0`；标题 `#101820`；正文 `#303030`；次级 `#6F7275`；线条 `#C9CDD1`；强调 `#12355B`

> **硬门槛**：用户能在对话里直接看到 8 张样张图之前，不能进下一步。

### 步骤 3：环境能力核查 + 降级决策（关键转折点）

**发生了什么**：
- 按 cyber-ppt 标准流程，逐页蓝图本应由 **ImageGen（图像生成）** 生成 16:9 位图。
- 核查发现：**环境没有任何图像生成能力**；当时也没有 LibreOffice 渲染器。
- 这是硬门槛缺失，不能假装跳过。

**决策过程**：
- 用户先选"换环境再做"（方案B）。
- 用户回来报告：图像生成搞不定，但装好了 LibreOffice、pptxgenjs、python-pptx+Pillow。
- 补装 PyMuPDF 后，渲染链路全通。
- 最终定下**降级路径**：跳过 ImageGen 蓝图（记录 `imagegen_skipped_by_user=true`，依据=已确认的风格4样张+锁定视觉系统），用 **PptxGenJS 原生生产 + LibreOffice 渲染 QA**。

> **核心教训**：遇到环境限制要**如实告知 + 给可选方案**，不能假装满足硬门槛。降级也要留痕。

### 步骤 4：搭建共享视觉模块（theme.js）

**做了什么**：把锁定的风格4固化成一个可复用的 JS 模块 `build/theme.js`，包含：
- 画布尺寸（13.333×7.5in）、安全边距、内容宽
- 完整色板（bg/paper/title/body/sub/line/accent/warn/pos/neg…）
- **固定 15 级 Typography Scale**（C0 封面，T1–T14 内容页），字号写死，不临时发明
- 字体（中文苹方 PingFang SC，代码 Menlo）
- 通用元素函数：`addBase`(徽章+页脚)、`addTitle`(标题+强调规线)、`addFooter`、`addSoWhat`(底栏)、`addKPI`、`addPanel`、`addClaim`(结论条)、`addTable`、`addCode`、`addPill`

> **价值**：两份 PPT 共用一套视觉系统，保证品牌统一、风格不漂移。改一处，两份都跟着变。

### 步骤 5：先做 3 页风格验证样张（避免 35 页返工）

**做了什么**：在批量生产前，先做 3 页代表性样张（封面 + KPI内容页 + 表格页），渲染给用户确认"风格4 的最终执行观感"。
- 生成 → 渲染 → 发图给用户 → 用户说"风格 OK"。
- **通过后才批量生产**。

> **核心方法论**：先小步验证视觉执行，再大规模生产。这避免了"做完 35 页才发现风格不对"的灾难。

### 步骤 6：逐份生产（PptxGenJS + 渲染 QA + 结构自检）

**PPT1 生产**：
1. 写 `build-ppt1.js`（17 页，全部用 theme.js 的函数搭建）。
2. `bun run build-ppt1.js` → 生成 PPTX。
3. `bash render.sh` → 渲染每页 PNG。
4. **结构自检**（python-pptx 脚本）：查零尺寸、负坐标、右越界、下越界。
5. 发渲染图给用户审阅。

**发现并修复的问题**：
- **P7 中心架构图遮挡**：连接线画在中心节点之上（z-order 错），斜线穿过中间内容。修复：先画线（底层）→ 再画中心节点 → 最后画四角卡片，让线从节点边缘接出。
- **零尺寸告警**：流程连接线用 `w:0` 的垂直线触发自检告警，改成 `w:0.02` 的细矩形消除。

**结构自检脚本**（复现必备）：
```python
from pptx import Presentation
prs = Presentation('xxx.pptx')
W,H = prs.slide_width/914400, prs.slide_height/914400
for i,sl in enumerate(prs.slides,1):
  for sh in sl.shapes:
    l,t,w,h = sh.left/914400,sh.top/914400,sh.width/914400,sh.height/914400
    if w<=0 or h<=0: print(f"P{i} 零尺寸")
    if l+w>W+0.05: print(f"P{i} 右越界")
    if t+h>H+0.05: print(f"P{i} 下越界")
```

### 步骤 7：方向纠偏（PPT2 重写）——最重要的实战教训

**发生了什么**：
- PPT2 第一版按源材料标题做成"成本优化"方向（5×成本警示、降本四法则、Token KPI）。
- 做完 18 页发给用户，用户反馈：**"成本优化不是我需要考虑的事情，我要做的是让团队成员可以更好地使用 CIMICode 和大模型。重写。"**

**怎么处理的**：
1. 立即承认方向性错误，不狡辩。
2. 提出新方向（用好 + 团队赋能）+ 新结构（18 页），**先让用户确认新结构再重写**（避免又跑偏）。
3. 删掉全部成本内容，保留并强化"用好"内容（AGENTS.md/Plan-Build/Skill/Prompt/DOE/业务场景/落地）。
4. 重写 `build-ppt2.js`，删除旧版 PPTX，重新渲染交付。

> **核心教训**：
> - **源材料的标题 ≠ 用户的真实意图**。材料叫"成本优化"，但用户要的是"用好"。
> - 发现理解错意图要**果断重写**，不要在小修小补上浪费时间。
> - 重写前**先确认新结构**，因为已经错过一次方向。

## 四、关键方法论与实战教训（PPT3 的灵魂）

### 4.1 六条核心实践

| # | 实践 | 说明 |
|---|---|---|
| 1 | **证据表先行** | 每个事实/数字都有来源，不臆造、不用常识补数据 |
| 2 | **确认门要重** | 故事线/页数/逐页论点/密度一次确认，不只在标题层面确认 |
| 3 | **先验证风格再量产** | 3 页样张确认视觉执行，再批量生产，避免大面积返工 |
| 4 | **结构自检** | 每页查零尺寸/越界，用脚本而不是肉眼 |
| 5 | **AI 局限要诚实** | AI 无法读图 → 渲染图交给人审；缺图像生成 → 如实降级留痕 |
| 6 | **方向错了果断重写** | 理解错意图立即推翻重来，不在错误方向上修补 |

### 4.2 三个"反常识"认知

1. **大模型的价值在"端到端动手"，不在"聊天"**：它能生成文件、渲染、自检、迭代，把活真正干完。
2. **环境能力决定方法路径**：有没有图像生成、有没有渲染器，直接决定能用哪套流程。先核查再动手。
3. **降级不等于失败**：跳过 ImageGen 蓝图、改用人审视觉，照样交付了高质量可编辑 PPT——关键是如实留痕。

### 4.3 效果数据的诚实口径
- 源材料里的百分比（如"成本降60%"）多数是预估/目标值，**未实测**。
- PPT 中统一标注"预估/待实测"，绝不包装成已实现成果。
- PPT2 最终把"效果指标"页改成"可观察信号"（采用率/复用数/沉淀量），不用未实测百分比。

## 七、踩坑记录（避坑指南）

| 坑 | 现象 | 解法 |
|---|---|---|
| **意图理解错** | PPT2 做成"成本优化"，用户要的是"用好" | 重写前先确认新结构；源材料标题≠真实意图 |

| **AI 无法读图** | 模型不支持图像输入 | 渲染图发给人审；AI 负责结构与迭代 |
| **效果数据失真** | 把预估%当实测成果 | 统一标"预估/待实测"或改用可观察信号 |

## 九、给 PPT3 的叙事建议（供下一步制 PPT 参考）

PPT3 的故事线可以是：**"一次真实的大模型实践：我们如何用编程智能体把两份文字变成两份咨询级 PPT"**。

可能的 SCR：
- **S**：团队有大量文字材料想转成 PPT，但手工做慢、风格不统一。
- **C**：直接让大模型"做 PPT"往往得到模板化、不可编辑、内容失真的结果。
- **R**：用"证据分析→风格锁定→环境核查→模块化生产→渲染QA→方向纠偏"的工程化方法，让大模型产出可复现的高质量可编辑 PPT。
